# WP26 — Kanban card anatomy

Gives the board card the shape an operational board actually needs — record key, entity icon,
priority and status indicators, a completion meter, and the people responsible — and removes the
drag knob from the pointer experience, where the card itself is already the drag source.

`avatarInitials()`, `icon()`, and `safeHref()` are consumed as existing public helpers.

## The move handle stops being pointer furniture

Since WP25 the card itself is the drag source, so a permanently visible knob is decoration that
competes with the card's real content. It is still the only keyboard pickup affordance, so it is
hidden rather than deleted.

- `moveHandle: 'keyboard' | 'always'`, default `'keyboard'`.
- `'keyboard'` keeps the button in the DOM, in tab order, and fully announced, but visually
  clipped until it takes focus — or while it holds a grabbed card. A pointer user never sees it;
  a keyboard user tabs once from the card and it appears.
- Revealing runs on `:focus`, not `:focus-visible`. A committed pointer drop focuses the handle
  programmatically, and `:focus-visible` does not match after pointer input — which would leave
  keyboard focus sitting on a one-pixel control. The focus ring itself stays on `:focus-visible`.
- `dragFrom: 'handle'` overrides the option entirely: the handle is then the only thing a pointer
  user can grab, and a drag source nobody can see is not a control.
- `'always'` is the WP25 presentation: the handle joins the card's action group on hover and focus.
- There is deliberately no `'never'`. WP20 requires every movable card to expose an accessible move
  handle and WP25 requires every pointer capability to keep its keyboard equivalent; the context
  menu is not a substitute, because it offers no destination index and therefore cannot reorder
  within a column. A mode that quietly drops the only conforming keyboard route is not the
  application's choice to make.

## Card anatomy

Two Kanban-owned regions bracket the shared record-card anatomy inside `.zx-record-card__body`:

```
head      entity icon · identifier                    status · priority
eyebrow   (shared slot fields — category, due date, …)
header    (shared selection, title, subtitle, actions)
metadata  (shared visible fields)
rules     (WP25 rule badges)
footer    progress meter
          assignee avatars
```

Both regions are omitted entirely when their options are unset, so an existing board renders
exactly as it did before.

- `entityIcon` — icon name or `(record, index) => string|null`, drawn before the identifier.
- `identifier` — field id or reader for the stable record key (`KAN-101`).
- `priority` / `status` — field id, reader, or a literal `KanbanIndicator`
  (`{label, tone, icon, dot}`). A plain value becomes the label; `priorityTones` / `statusTones`
  map that value to a semantic tone. A reader may return a `Node`, which is adopted as-is. Each
  badge is preceded by visually hidden text naming what it measures, because "High" on its own
  does not say high what.
- `progress` — field id or reader returning a number, or `{value, max, label}`. `progressMax`
  (default 100) sets the scale, so a 0–1 fraction is expressed as `progressMax: 1` rather than
  guessed at. Renders a labelled `role="progressbar"` meter.
- `assignees` — field id or reader returning a name, a list of names, or `{name, src, initials}`
  entries. Renders up to `maxAvatars` (default 3) avatars plus a `+n` overflow chip. Image URLs
  pass through `safeHref`; the group carries one accessible name listing everyone, and the
  individual chips are hidden from assistive technology so the list is announced once. The face
  count and the chip count come from one normalization (`kanbanAvatarLimit`) so they cannot
  disagree.

Anatomy readers are resolved once per refresh, not once per card: a field id otherwise costs a
full `getFields()` clone every time it is read.

A field consumed by the head or footer is dropped from the shared metadata list, so the same value
is never shown twice. `field.duplicate === true` opts back in, matching how title and subtitle
already behave.

`renderCard` replaces the shared record-card content — eyebrow, titles, metadata. The Kanban head
and footer answer to their own options and still render, because setting `progress` is a request
for a meter regardless of who draws the middle of the card. Clearing those options is what removes
them.

Identifier and indicator prefixes are real, visually hidden text rather than `aria-label`, which
is prohibited on the generic role a `<span>` reports.

Avatars are deliberately uniform rather than per-person colours: components may only consume
semantic tokens, and the shared `Avatar` is neutral for the same reason.

## Empty columns

`columnEmpty` now defaults to a drop-target message instead of an empty string, so an empty column
reads as somewhere a card can go rather than as a rendering gap. `renderColumnEmpty` still replaces
it, and `labels.columnEmpty: ''` restores the previous blank column.

## Out of scope

- Rendering swim lanes as a left label rail instead of stacked sections.
- A card editor, inline editing, or any write path. These options are read-only projections.
- Per-person avatar colours, presence, or an avatar component instance per card. The card stays
  listener-free and creates no components.
- Changing the quiet column-count treatment settled in 4.3.3.

## Acceptance criteria

1. With no new option set, a board's cards carry no head, footer, or rule badges. The move handle
   is the one deliberate change from 4.3.4: it is clipped until focused unless `moveHandle:
   'always'` or `dragFrom: 'handle'` says otherwise.
2. No knob is visible to a pointer user by default, and a keyboard user can still grab, move,
   cancel, and drop a card with the WP25 key map.
3. Indicator, progress, and avatar content is text-safe: values reach the DOM as text, image URLs
   through `safeHref`, and a reader's `Node` is adopted rather than parsed.
4. The progress meter exposes `role="progressbar"` with min, max, now, and an accessible name.
5. The avatar group is announced once, naming everyone including the overflow.
6. A blank progress label, a fractional `maxAvatars`, and a literal indicator descriptor all
   produce correct output rather than an unnamed meter, hidden faces, or nothing at all.
7. `npm test` and `npm run test:browser` pass; creating and destroying the view twice leaks
   nothing new.

## Release

New public options are backward-compatible additions, so this is a **minor** release (4.4.0), not
a patch. `moveHandle` and `columnEmpty` also change established defaults; both are documented in
the changelog with the one-line opt-out that restores 4.3.4 behavior.
